# 0.9.6 — the correctness release

Six packages: `gitcad`, `gitcad-core`, `gitcad-mech`, `gitcad-ecad`,
`forgekernel`, `forgekernel_rs`.

This release ships **no new capability**. The matrix is 327/345 in 0.9.5 and
327/345 here. What changed is that several answers which were wrong are now
right, and the machinery that failed to notice has been widened.

## Breaking: geometry output changed

**`chamfer` was removing 2d³/3 more material than any edge asked for.** A
corner-facet pass truncated every vertex, but at a box corner the three chamfer
planes already meet at the single point (d/2, d/2, d/2) — the apex is a vertex,
and there was no corner face to cut. Cutting one anyway removed a tetrahedron
per corner.

    box            0.9.5        0.9.6      V = abc − 2(a+b+c)d² + 6d³
    20×20×20 d=2   22688/3      7568
    30×20×10 d=1   17656/3      5886
    40×30×20 d=3   22524        22542

If you have a part with chamfers, **its volume and mass will change**. This is
a deliberate divergence from a recorded OCCT reading, taken because a point
clearing all twelve edge half-spaces was being silently removed. If you need
OCCT-compatible chamfer semantics for interop, open an issue — it belongs
behind an explicit flag, not as the default.

## Breaking: `check_interference` can now return `ok=False` where it returned `ok=True`

Two independent causes, both fixed:

* **A pointed cone's apex was missing from its bounding box** — it is a
  singular point on no edge, so `bbox` never visited it and the box collapsed
  along the axis (`measure()["dz"] == 0.0` for a 20 mm solid). Interference
  uses the AABB as a skip-filter, so a peg sitting *entirely inside* a cone
  came back clear with zero pairs even attempted.
* **A pair the kernel cannot evaluate is now UNDETERMINED, not clear.** It is
  listed in `checks["undetermined"]` with the stage that refused, and it blocks
  `ok`. A clearance check that cannot compute an answer has not found
  clearance.

## Fixed: drawings that were silently blank

`hlr_project` and `section_polys` returned empty results for **19 of 52**
buildable shapes — every rounded box, every filleted or shelled drilled part,
both sphere overlaps. Three bare `except Exception:` were swallowing an
`AttributeError` from a mesher call. Nothing raised, so the capability matrix
scored those cells `ok`.

    filleted box projection      0/0    →  61 visible / 47 hidden
    filleted box section          []    →  40 segments
    blank projections in corpus    19   →  0

`section_polys(deflection=…)` was also silently discarded on the mesh path (52
segments at every deflection, 0.2 down to 0.001); it now responds.

## The audit that should have caught these

Three changes, because the pattern across every defect above is the same: the
check and the thing being checked drifted apart.

* **The answer audit was skipping most answers.** It ran only on canonical
  `Body` objects, and most results are not — `Cyl`, `DrilledSolid`,
  `AxisStack`, `DisjointUnion`, `RoundedBox`… It now converts first, so it
  covers every representation with a canonical form.
* **Orientation is now checked.** Edge pairing counts *uses*; it is blind to
  *direction*, and a face whose loop runs backwards passes it outright. The new
  closed-shell vector-area check (`Σ Aᵢn̂ᵢ = 0`, a boundary integral, exact in
  ℚ) catches it. Bodies carrying arcs return "not checked" rather than a
  partial sum.
* **One mesher.** `tessellate` preferred each representation's own mesher over
  the canonical one; measuring showed the canonical path strictly better on
  every curved shape, and several representations silently discarded the
  caller's deflection.

## Known limits, unchanged

16 capability gaps remain, all honest refusals. Two cells are outside any exact
field permanently and are marked as such rather than counted as backlog. The
differential oracle resolves errors down to ~0.2%; below that is a stated blind
spot, not a guarantee.

`vector_area_defect` does not yet cover arcs. The term is
½[c × (p₁ − p₀) + r²Δθ n̂], exact in ℚ[π] via the twelfth span.
